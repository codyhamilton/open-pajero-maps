# Independent review of 3-10 count-wrap recon

VERDICT: ACCEPT

Reviewed `triage/count_wrap_recon.md` against `briefs/3-10-count-wrap-recon.md`, `output/scratch-3-09m/mask_measure.md`, `output/scratch-3-10/` (scan.py, unit_detail.py, orig.json, G311b.json, unit_detail_full.json, table2.md), `parser/kiwiw/_cenc.c` L735-790, `_d1.c` L205-262. Read-only; light python over existing JSON only; no builds or K1 runs.

## Findings

1. (low) Mechanism confirmed. `_cenc.c` L781-786 writes `(class_n[c] & 0xFFF) | (c << 14)` while `class_n[c] += nrec` counts every written record, so wrap = physical - declared = 4096 is exact. From `G311b.json`: 41 `big` entries in 37 distinct cells, every one with `physical - declared == 4096`, every one a single class-2 unit, max physical 6415, all 41 under 2 x 4095, so one extra unit suffices. The table (41 rows) was recomputed against `G311b.json` (declared, physical, bg_len, and headroom = 131070 - bg - 4): 0 mismatches. The 4-element cells are (1711,729) x2 and (1915,980) x4, as stated.

2. (low) Host-reader claim verified. `_d1.c` L229-262: loops `n` unit headers, takes each unit's `val & 0xFFF` count and `val >> 14` class, reads records sequentially, appends to flattened shape tables (sum, no overwrite); offset word stored but unused. R scan: `mism: 0` over 4,157,312 elements means declared-sum == physical walk in all multi-unit R elements, consistent with summing. Caveat stated in the recon is correct: host tools only.

3. (low) Original-disc numbers verified from `orig.json` and `unit_detail_full.json`: elements 4,157,312; nunits hist 1:4,099,619 / 2:52,895 / 3:4,771 / 4:27; `dup_class_elems` 57,693; class order [2,2] 52,096, [2,2,2] 4,771, [2,2,2,2] 27, [1,1] 799; `dup_overlap` 0, `dup_disjoint` 57,693; `max_unit_decl` 517; `max_class_sum` 585; resbits 0, hflag 0; `boff_eq_actual` all 4,157,312. The "type-disjoint" claim rests on `unit_detail.py`, which in the saved run covered every element (elems = 4,157,312), so it is a full result, not a sample.

4. (medium) Risk statement is honest but could say more about what is established. Established: R has multiple same-class units, each seen with different type codes; no R unit exceeds 517 records. Not established: (a) same-class AND same-type units; (b) any unit above 4095 (so the firmware may use a 12-bit count in a way where 4095 is fine, but nothing shows bit 12 is ignored vs the count); (c) the firmware may key on the offset word (R writes the true offset in all elements, G writes 0 in all 1,420,999 elements, `boff_nonzero` 0). If firmware uses the offset word to locate units, G is already off-convention and a split design should carry correct per-unit offsets; the recon lists the offset word as open item 2 but does not link it to the split risk. Also not mentioned: using bit 12 as a 13th count bit (all 41 cells < 8192) is a format guess too (R keeps it 0), weaker than the split; worth listing in Q5 for completeness.

5. (medium) Envelope gap not stated. R's per-level max class sum at level 0 is 219 (overall 585), while G has 6415 records in one cell: G is about 11x R's maximum anywhere. The recon frames the issue as "no precedent for a unit above 4095" but the broader point is that G cells are well outside any original-disc density, so other firmware limits (per-frame record buffer, E2 render budget) are equally unobserved. This does not invalidate the recon, but 3-11 should not treat "R max 517" as a safe reference.

6. (medium) Re-oracle scope: Perth overlap is computable now and the recon left it unmeasured. Perth fixture bbox is `FIXTURE_BBOXES["perth"] = (115.5, -32.5, 116.5, -31.5)` (`parser/kiwiw/mesh.py` L405). At level 0 the cell grid is 0.03125 x 0.020833 deg from (90, -50), so Perth covers about ix 816-848, iy 840-864. The 37 cells have ix >= 872 (smallest is (872,880)); none intersects. So Perth sha `da13a775...` is expected unchanged (the build drops all cells outside the fixture bbox). Inference from bbox arithmetic, not a measured Perth scan; 3-11 should still record the Perth sha and expect no move. Full-AU sha `87a01b14...` moves by construction; the differing cell set should be exactly the 41 elements in 37 cells (any extra is a stop per the template).

7. (medium) Whole-frame headroom of the other 36 cells remains unmeasured; recon says so. Derived bound from data: golden frame 131060 B vs bg 130096 B means 964 B of non-bg content in that cell. The cells with least bg headroom after the split are (1681,729) 2936 B and (1929,1121) 5394 B, then (1530,844) 8330 B; these are the ones where road/name content could push the whole frame past 131070. Cheap to measure before 3-11 (sum all sub-frame sizes per leaf for the 37 cells; the scan's `frame_end` is unusable as noted). Make this a 3-11 pre-edit check, or a one-line recon addendum.

8. (low) Golden scope: only `l0_divided_trim_halo` (window 1755 591 1756 592) was identified as containing a wrap cell. The claim "other goldens do not contain these cells" was not shown with a window list. Quick check against `docs/provenance.md` goldens table recommended in 3-11; K1 completeness row counts shifting declared -> physical is correctly characterised as intended.

9. (low) Sizing: recon says capacity 4 units today and 5 needed for a split. Confirmed in `enc_bg`: `n_units` is capped by 4 classes by construction, `n_in`/`unit_off`/`rec0` sized for that; the squeeze `memmove` only handles n_units < n_in, so a split needs the up-front sizing changed, not just the count write. Header `esz`/`out[4..5]` derive from `p`, so +4 B flows through. Not a defect in the recon.

## Bottom line
No blocker or high finding. The mechanism, 37 cells/41 frames, the R-disc statistics and the reader behaviour all reproduce from the saved data. The orchestrator should put the same-class-same-type unit risk (finding 4, plus the offset-word link and the density envelope in 5) to Cody before authoring 3-11, and fold the whole-frame headroom measurement (7) and the Perth no-overlap expectation (6) into 3-11's pre-edit checks.
